# Dispatch Shell — Presentation Layer — NOTES

Branch: `build/dispatch-shell`. Packet:
`docs/website/DISPATCH_SHELL_LAUNCH_PACKAGE_v1.md`. Not a governed "lane"
in the A/B/C/D sense — no forbidden-file boundary conflicts with any of
them, since it only ever imports their public entry points.

## Built

- `src/dispatch/shell/app.py` — `create_app(config)`: the shell's own
  small Flask app (`/`, `/pilot`, `/pilot/process`), wrapped in
  `werkzeug.middleware.dispatcher.DispatcherMiddleware` mounting
  `dispatch.queue.app.create_app(config)` at `/queue` and
  `dispatch.reports.app.create_app(config)` at `/reports` — both called
  exactly as their own modules expose them.
- `src/dispatch/shell/templates/{base,dashboard,pilot}.html` +
  `static/style.css` — the shell's own copy of Reports' existing minimal
  look (system font, ~18px base, `#fafafa` background), not shared
  cross-app.
- `src/dispatch/shell/README.md`.
- `tests/shell/` — 15 tests: both mounted apps reachable, their static
  assets resolve under the mount prefix, and — the one real technical
  risk this package carried — a link *generated by Queue's own template*
  (`url_for('item_detail', ...)`) resolves to `/queue/items/<id>` and
  actually works when followed, not just typed by hand. Plus: dashboard
  reflects real queue/pilot/report state (not fixtures pretending to be
  real), the Process Inbox button runs the real pipeline end to end,
  failure handling renders a clear error instead of a raw 500, a
  no-raw-SQL-write grep guard, and an AST-level check that the shell
  imports exactly one name (`create_app`) from each of
  `dispatch.queue.app`/`dispatch.reports.app` and nothing else from those
  two modules. Full repo suite: 358 passed.
- Small addition to `dispatch.pilot.intake.PilotIntake`: a public
  `close()` method, so the shell's `flask.g` per-request cleanup doesn't
  need to reach into a private `_conn` attribute. The only change to
  code outside `src/dispatch/shell/**` this package made — Pilot isn't
  one of the two lanes with a "zero diffs" requirement (only Queue and
  Reports are), and this addition is additive, doesn't change any
  existing behavior, and is covered by the existing `tests/pilot/` suite
  still passing unchanged.
- **Manual smoke test against the real running mounted server** — not
  just the test client. Seeded real queue items, a real Pilot inbox
  batch, and a real saved report; confirmed the dashboard showed the
  correct real counts; then, critically, followed a real
  `/queue/items/<id>` link generated by Queue's own unmodified template
  by clicking through (curl, not typed), confirmed its stylesheet
  resolved at `/queue/static/style.css`, did the same for `/reports/`,
  and finally exercised the real "Process Inbox" button end to end —
  both files (a fuel CSV and a RateCon) routed correctly, independently
  confirmed on the real filesystem afterward. Zero errors in the server
  log across the whole session. `git diff --stat integration --
  src/dispatch/queue/ src/dispatch/reports/` confirmed **zero diffs** —
  the "existing UIs untouched" claim is verified, not just asserted.

## Flagged

- `PilotIntake.close()` addition (above) — flagged explicitly since it's
  the one file this package touched outside `src/dispatch/shell/**`.
- The shell's own `/pilot` template and `/queue`'s/`/reports`' own
  templates are visually consistent (all three independently converged
  on the same minimal look during their own build sessions), but they
  are still three separate stylesheets, not one shared one — a
  deliberate consequence of "mount, don't merge" (§1 of the launch
  package), not an oversight.

## Deliberately Not Built

- No authentication, HTTPS, or reverse proxy — explicitly out of scope
  per standing direction, and restated as forbidden in the launch
  package itself.
- No merge of Queue/Reports into the shell's own process beyond WSGI
  mounting — their route definitions, templates, and static files remain
  100% theirs, by design (§1 of the launch package: "not a redesign, a
  merge, or a rewrite").
- No background-job handling for a large Inbox — flagged as a risk in
  the launch package (§10, risk 3), not a concern at current pilot scale
  (`docs/pilot/DISPATCH_PILOT_RUN_1_REPORT_v1.md`), not solved
  preemptively.

## Deferred

None — every acceptance criterion in the launch package's §7 was met and
verified live in this session, not left open.
