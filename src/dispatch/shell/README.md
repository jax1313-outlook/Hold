# dispatch.shell — Mike's one bookmark

Per `docs/website/DISPATCH_SHELL_LAUNCH_PACKAGE_v1.md`: one URL, one
port, three real screens (`/queue`, `/reports` — both existing apps,
completely unmodified — plus a new `/pilot`), and a home dashboard.

## Mounting, not merging

`create_app(config)` builds the shell's own small Flask app (`/`,
`/pilot`, `/pilot/process`), then wraps it in
`werkzeug.middleware.dispatcher.DispatcherMiddleware`, mounting
`dispatch.queue.app.create_app(config)` at `/queue` and
`dispatch.reports.app.create_app(config)` at `/reports` — their own
`create_app()` functions, called exactly as every other consumer would
call them. Nothing under `src/dispatch/{queue,reports}/**` is imported
for its internals, subclassed, or edited; this module only ever calls
their one public entry point each.

Werkzeug sets `SCRIPT_NAME` per mounted app, which Flask's `url_for`
respects automatically — so Queue's and Reports' own templates
(`url_for('static', ...)`, internal links, form actions) resolve
correctly to `/queue/...` and `/reports/...` with zero changes to their
route definitions. This is the one real technical risk in this package
and is verified two ways: `tests/shell/test_app.py` exercises the
mounted routes through the test client, and the manual smoke test
(`docs/website/NOTES.md`) clicks through the real running server,
following links generated by Queue's and Reports' own templates rather
than typing URLs directly — exactly the class of thing this project has
learned not to trust from documentation alone (Lane B's threading bug
and Lane D's two lazy-schema bugs were all caught the same way).

## Zero new writes

The shell issues no SQL of its own — ever. Every read goes through
another lane's own real, already-governed public read API:
`QueueStore.list_all()` (Lane B), `dispatch.reports.snapshot.recent_reports()`
(Lane D, over the same `readonly.open_read_only()` connection Reports
itself uses), and `PilotIntake`'s folder properties (Pilot). The one
write action — the "Process Inbox" button on `/pilot` — calls
`PilotIntake.process_inbox()` directly, the exact same function a
terminal invocation would call; the shell doesn't wrap it, retry it, or
change its behavior. A failure there renders a clear error on the page
instead of a raw 500 (`RECEIPT_CONSTITUTION_v1`'s "never fabricate,
never crash silently" instinct applied to a write route).

## Connection lifetime

`flask.g`, one connection per request, closed in `teardown_appcontext` —
the same pattern Lane B's and Lane D's own apps use, for the same reason
their docstrings already document: the real dev server's request
threads are not guaranteed to be the thread `create_app()` ran on.

## Dashboard content

Open queue items grouped by priority (`urgent`/`today`/`whenever`, the
same three doors Lane B's own UI uses), DispatchPilot's current folder
counts (including the Inbox itself), and the last three saved reports
(Lane D's own "recents" concept, reused directly rather than
reimplemented). Viewing the dashboard writes no audit entry — matching
Reports' own established precedent that a plain read is not a governed
action worth logging.
